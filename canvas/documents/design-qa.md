## 1. 产品与定位

### Q1：这是一款什么游戏？

一款以「打工人反坑画饼老板」为题的**竖屏短局动作游戏**。玩家扮演牛马员工，在办公区潜行、整蛊、飙椅、反弹黑锅，最终在第 16 关把老板炒掉。

它更接近「**街机式关卡合集**」而不是长线养成：一关一个玩法、一个目标、一次结算，靠模式切换维持新鲜感。

### Q2：目标玩家和游玩场景是什么？（推断）

- 18–35 岁、熟悉网络职场梗的移动端用户；
- 碎片时间游玩：地铁、排队、午休，单局 1 分钟左右；
- 偏好即时反馈和夸张演出，不愿学习复杂操作或阅读长教程。

### Q3：和普通潜行游戏最大的区别？

| 普通潜行 | 本作 |
| --- | --- |
| 被发现 = 失败/读档 | 被发现只是扣星、被追，仍可甩掉 |
| 鼓励等待与观察 | 鼓励主动出击、制造混乱 |
| 单一潜行循环 | 每 3 关切换一次玩法内核 |
| 严肃军事/谍战题材 | 办公室日常 + 网络热梗 + 夸张卡通 |

设计取舍：**降低惩罚、提高表达**。玩家失败时应该想「再来一把」，而不是「我不适合这游戏」。

### Q4：情绪基调？

不是苦大仇深，而是「**笑着掀桌**」：老板是漫画式反派，整蛊是夸张物理喜剧，结算用烟花和三星庆祝。文案大量使用「颗粒度」「对齐」「自愿团建」等职场黑话做反差笑点。

## 2. 核心循环

### Q5：一局的循环是什么？

```
选关（看目标/提示/首通星级）
  → 开局聚光灯锁定目标与路线
  → 摇杆/点地移动 + 看准时机互动
  → 目标达成 → 结算（1–3 星 + 用时 + 统计）
  → 解锁下一关 / 重打刷三星
```

### Q6：关卡之间靠什么推进？

- **章节推进**：5 章，每章 3–4 关，章节主题与配色不同；
- **星级收集**：16 关 × 3 星 = 48 星，选关页顶部汇总；
- **叙事递进**：从「卡点打卡」到「炒掉老板」，冲突逐章升级，第 16 关是毕业决战；
- **无强制解锁门槛（实现现状）**：所有关卡卡片可直接点选，章节 Tab 自由切换，方便体验与测试。

### Q7：失败和重试的成本？

- 失败只展示结算弹窗，按重试/空格立即重开；
- 单关 45–90 秒，重试几乎无沉没成本；
- 存档只记录每关最高星级，不会因失败丢进度。

## 3. 关卡结构

### Q8：为什么是 16 关、5 章？

16 关足以让 11 种模式各出现 1–2 次，并形成「教学 → 变奏 → 决战」的节奏；5 章对应 5 种情绪段落：潜行、整蛊、物理、反转、掀桌。每章 3–4 关，刚好一顿碎片时间能打完一章。

### Q10：难度曲线怎么设计？

不是靠数值堆叠，而是靠**规则复杂度**爬坡：

1. 1–3 关：单 Boss、无监控、明确两步目标（教学）；
2. 4–6 关：从「躲」转「主动整蛊」，需要组合操作（引位 + 互动 + 抓拍）；
3. 7–9 关：实时动作与瞄准，操作精度要求上升；
4. 10–15 关：多目标管理、资源管理（人数、耐久、协议数量）；
5. 16 关：综合考试，三阶段 Boss 同时考走位、反弹、机关利用和终结互动。

数值上，守卫视野/速度、目标数量、限时都逐章收放，PAR 时间给三星留出熟练空间。

### Q11：关卡是怎么组织进代码的？

数据驱动：`src/campaignLevels.js` 的 `CAMPAIGN_LEVELS` 是唯一关卡源。每关声明地图模板、玩家出生点、守卫巡逻点、摄像头、可互动物件、道具、目标文案、`modeConfig`。`stealthGame.js` 的 `createStealthGame(level)` 读取配置后生成运行时状态，`main.js` 只负责表现与输入。

新增关卡主要是**加配置**，不需要改渲染与主循环。

## 4. 玩法模式

### Q12：11 种模式分别是什么？

| 模式 key | 玩法一句话 | 出现关卡 |
| --- | --- | --- |
| `stealth` | 躲视野、借掩体与声东击西完成目标 | 1–3 |
| `prank_hunt` | 主动设局整蛊 Boss（吹假发/保龄球/黑暗特调） | 4–6 |
| `chair_derby` | 骑转椅漂移 + 氮气冲撞拆目标 | 7–8 |
| `pot_pong` | 看准时机挥平底锅反弹黑锅 | 9 |
| `wake_coworkers` | 巡逻拍醒打瞌睡队友，别让 Boss 抓包 | 10 |
| `be_the_boss` | 角色反转，用喇叭揪出躲藏的摸鱼怪 | 11 |
| `desk_defense` | 键盘拍飞/踢椅清场，守住下班工位 | 12 |
| `shredder_race` | 与 HR 抢降薪协议，抱去碎纸机 | 13 |
| `vault_heist` | 推椅压重力板解谜，抱年终奖跑路 | 14 |
| `blackout_escape` | 拉闸制造黑暗，借夜色潜行到电梯 | 15 |
| `final_boss` | 三阶段综合决战 + 终结演出 | 16 |

### Q13：为什么一关只做一个模式，而不是大杂烩？

- **学习成本**：单局 60 秒，玩家没时间理解多套规则；
- **反馈清晰**：一关只回答一个问题（能不能躲？能不能撞？能不能拍回去？）；
- **可复用**：所有模式共享同一套地图网格、角色、道具、HUD 与结算，边际成本低。

### Q14：模式之间共享哪些底层系统？

移动与碰撞、寻路 `findGridPath`、视野锥 `canObserverSeePlayer`、交互半径、道具栏、转椅物理、抛射物、眩晕/无敌帧、时间与星级、事件流（飘字/音效）、渲染管线。模式差异主要体现在 `modeConfig` 参数与少量分支逻辑。

### Q15：想加第 12 种模式，要动哪里？

1. `campaignLevels.js`：写新关卡的 `mode` 与 `modeConfig`；
2. `stealthGame.js`：加模式初始化、`step` 分支、胜负判定、`getActionDescriptor`、快照统计；
3. `main.js`：在 `MODE_META` 加配色/图标/操作文案，必要时加专属 HUD 或按钮；
4. `officeRenderer.js`：复用现有道具；若需新物件，加绘制分支；
5. `tests/stealth.test.js`：补一条可通关的自动化用例。

## 5. 操作与反馈

### Q16：输入方案是什么？（实现现状）

- **虚拟摇杆（左下）**：推动移动，推到底自动冲刺；有体力消耗；
- **点地图寻路**：点地面/物件/同事/椅子，自动寻路并执行对应交互；
- **互动大按钮（右下）**：随模式变化（打卡、抓拍、反拍、塞碎纸机、揪出摸鱼……）；
- **副按钮**：踢椅、氮气、纸箱隐身等；
- **两个道具槽**：洗洁精、冰美式、发条青蛙、泻药等；
- **键盘兼容**：方向键/WASD 移动，Shift 冲刺，E/空格互动，Q/1、2 用道具，M/Esc 选关，R 重开，H 提示。

### Q17：为什么保留「点地寻路」而不是纯摇杆？

手机用户常常单手玩，摇杆精度不足以对准 30px 的互动点。点地寻路把「走到哪、做什么」压缩成一次点击，同时保留摇杆给需要走位躲视野的动作关。

### Q18：反馈分成哪几层？

| 层级 | 表现 |
| --- | --- |
| 即时 | 按钮按下缩放、音效、短震动、点击涟漪 |
| 目标 | 聚光灯圈出下一步目标、箭头指引、任务条更新 |
| 事件 | 飘字（+星、-秒、被抓）、粒子、屏幕震动、白闪、慢动作 |
| 角色 | 表情/心声气泡、假发飞出、秃头反光、Boss 红温 |
| 结算 | 星级点亮动画、烟花、毕业礼花、评语与统计 |

### Q19：新手怎么学会玩？

- 开局 3.2 秒聚光灯自动锁定当前目标，玩家一动就淡出，不打断；
- 选关页每关有 3 条提示（hints）和故事文案；
- 当前目标常驻底部任务条，取关切换目标时会再次打聚光灯；
- 互动按钮文案直接写动作（「反拍黑锅」而不是「互动」），不需要记规则。

## 6. 难度与星级

### Q20：限时与 PAR 时间分别起什么作用？

- **限时**：失败边界，制造紧张感；
- **PAR**：三星门槛，熟练玩家的目标；
- 限时与 PAR 的差值即「熟练度空间」，如 Lv1 75s / 35s。

### Q21：三星规则是什么？（实现现状）

| 模式组 | 第 1 星 | 第 2 星 | 第 3 星 |
| --- | --- | --- | --- |
| 动作/反击类（pot_pong、chair_derby、be_the_boss、shredder_race、final_boss） | 通关 | 失误/被发现 ≤ 1 次 | 快于 PAR 或整蛊 ≥ 3 次 |
| 守护类（wake_coworkers、desk_defense） | 通关 | 零失误/被发现 | 整蛊 ≥ 1 次或工位零损伤 |
| 其余（潜行/整蛊/解谜） | 通关 | 零失误/被发现 | 整蛊 ≥ 1 次 |

设计意图：三星不只奖励「快」，也奖励「玩得花」和「干净利落」，给不同风格玩家留出路径。

### Q22：被发现的惩罚有多重？

潜行类被发现进入追击，甩掉后 suspicion 回落，不直接判负；动作类被击中扣时间、短眩晕、给 0.8 秒无敌帧。整体是「**可恢复的惩罚**」，避免一次失误毁掉整局。

## 7. 老板捏脸工坊

### Q23：为什么做「捏老板」？

把抽象的「老板」变成玩家自己定义的具象反派，增强代入感和分享欲。名字、口头禅、外形都进入剧情与战斗台词，整蛊对象越具体，笑点越强。

### Q24：自定义影响哪些地方？

- 选关页横幅、剧情文案、Boss 心声与台词；
- 游戏内 Boss 立绘（发型、眼镜、西装、胡须、体型）；
- 所有 16 关通用；本地存档键 `niuma_custom_boss_v1`。

### Q25：自定义的边界？

- 名字最多 8 字，口头禅最多 18 字；
- 6 种发型 × 5 种眼镜 × 6 套西装 × 5 种胡须 × 3 种体型；
- 提供 6 个预设名字与 5 句预设口头禅，避免空白输入；
- 使用原生 DOM 输入框以兼容手机输入法，关闭后回到 Canvas 渲染。

## 8. 美术与音频

### Q26：为什么全部用代码绘制，不用图片资源？

- **风格统一**：描边、圆角、粉彩配色由同一套绘图函数控制，不会出现素材风格打架；
- **体积极小**：发布包仅约 232 kB JS（gzip 83 kB），首屏快；
- **易迭代**：改数值/改颜色即可调整，不需要重新导出素材；
- **动画自由**：假发飞出、秃头反光、转椅漂移、纸箱隐身都可用变换实时生成。

代价是美术上限和制作效率，详见 Q43。

### Q27：视觉语言是什么？

- **2.5D 俯视**：世界 960×620 横版坐标，旋转 90° 映射到 390×844 竖屏，产生等距感；
- **粗描边 + 粉彩**：统一墨色 `#2b2d42`，米白纸感底，章节各自一套三色渐变；
- **章节色**：第1章薄荷暖黄、第2章蜜桃暖阳、第3章珊瑚橙粉、第4章薰衣草霞光、第5章霓虹紫金；
- **区域标识**：茶水间、总裁室、工位区、前台大厅、摸鱼厕各有底色和标签；
- **情绪夸张**：红温、眩晕星星、问号/感叹号、心声气泡、聚光灯。

### Q28：音频是怎么工作的？

`src/bgm.js` 使用 WebAudio **实时合成**，无音频文件：

- 16 关各有独立曲目 + 菜单曲，步进音序器循环；
- 三档紧迫度：平时 / 时限 ≤15 秒或被追 / 时限 ≤7 秒，切换滤波与加花；
- 页面首次触摸/按键时解锁 AudioContext（兼容 iOS Safari）；
- 标签页隐藏时自动 suspend，回来 resume；
- 音效由 `main.js` 的 `sfx()` 合成：点击、成功、失败、被抓、反弹、氮气、毕业礼花等。

### Q29：程序化美术/音频的代价？

- 角色与场景细节有限，难做高质量过场；
- 新物件需要写绘制代码，不能直接用美术资源；
- 音乐是芯片感循环，缺乏情绪层次；
- 若未来要提升品质，可保留程序化 UI/特效，用生成或手绘资源替换角色、Boss 立绘与章节背景。

## 9. 技术架构

### Q30：技术栈与运行方式？

- Vite 6 + 原生 ES Modules，无 UI 框架；
- Canvas 2D 单画布渲染，requestAnimationFrame 主循环；
- WebAudio 合成音乐与音效；
- Node 内置 test runner 做逻辑测试；
- `npm run dev` 预览，`npm run build` 输出 `dist/`（相对路径，可任意托管）。

### Q31：模块职责怎么分？

| 模块 | 职责 |
| --- | --- |
| `main.js` | 主循环、输入映射、HUD/弹窗/特效、选关与结算、星级存档、BGM 调度 |
| `stealthGame.js` | 纯玩法状态机：地图、寻路、视野、守卫 AI、11 种模式、胜负与星级 |
| `campaignLevels.js` | 5 章 16 关配置 + 5 套地图模板（纯数据） |
| `officeRenderer.js` | 2.5D 场景绘制：地面、墙体、道具、角色、光照、心声 |
| `bgm.js` | 程序化 BGM 与解锁/紧迫度控制 |
| `bossCustomizer.js` | 捏老板工坊：DOM 输入 + Canvas 面板 + 本地存档 |
| `physics.js` / `prankSim.js` | **当前未被游戏引用**，早期原型/实验遗留 |

### Q32：坐标与分辨率怎么换算？

- 逻辑世界：960×620，18 列 × 13 行，格子 40px；
- 屏幕：390×844，格子 28px，地图左上角 (13, 84)；
- `P(x,y)` 把世界坐标转屏幕，`toWorld(sx,sy)` 反向转换；
- 所有绘制在 390×844 逻辑坐标下完成，`resize()` 按 DPR 放大画布。

### Q33：游戏状态归谁所有？

`createStealthGame()` 返回一个闭包对象，独占玩家、守卫、物件、抛射物、计时与胜负状态；`main.js` 只通过 `step(dt, input)`、`snapshot()`、`interactNearest()` 等公开方法与它交互。渲染层不写游戏状态，只读快照/对象，保证逻辑可被 Node 测试直接驱动。

### Q34：为什么不用 Phaser / Three.js？

游戏是规则驱动的俯视 2D，碰撞与寻路均为网格/圆形判定，不需要通用物理引擎或场景图。原生 Canvas 让包体、启动时间和调试成本最低，也便于精确控制手机 HUD 排版。

### Q35：性能边界在哪？

- 无贴图、无物理引擎、无逐像素处理，单画布每帧重绘；
- 主要开销是 Canvas 路径绘制与阴影/光效，粒子数量做了上限；
- 通过 `Math.min(devicePixelRatio, 3)` 限制高分屏像素量；
- 桌面与移动端实测流畅；若未来加入大量粒子或全屏滤镜，需要引入分层缓存。

## 10. 适配与发布

### Q36：如何适配不同尺寸和 iframe？

- `#app` 固定铺满视口，canvas 用 `aspect-ratio: 390/844` 与 `height: min(100dvh, ...)` 自适应；
- 内部始终按 390×844 逻辑坐标绘制，再整体缩放，所以任意 iframe 尺寸都不会溢出；
- 安全区使用 `env(safe-area-inset-*)`；
- 桌面端（≥600px）显示圆角手机外框，保留移动端气质。

### Q37：移动端和桌面端的差异？

- 移动端：触控摇杆、点地寻路、大按钮、震动反馈、首次触摸解锁音频；
- 桌面端：键鼠映射、Esc 选关、空格/回车确认、R 重开；
- 两端共用同一套逻辑与 HUD，仅输入层不同。

### Q38：发布产物是什么？

`vite build` 输出静态 `dist/index.html` + 哈希化 JS/CSS；`vite.config.js` 设置 `base: './'`，可在任意子路径托管。当前无后端、无网络请求、无账号系统。

## 13. 已知问题与技术债

### Q43：代码层有哪些遗留？

1. `src/prankSim.js`（约 970 行）未被任何模块引用，可删除或归档；
2. `src/physics.js` 只被测试引用，是早期物理实验残留，与现行玩法无关；
3. git 历史中的 Flutter 3D 验证提交与本项目无关，可考虑清理分支叙事；
4. 根目录没有 README，新人只能从代码理解项目——本问答即为补齐这一环。

### Q44：体验层有哪些待打磨点？

1. 第 16 关连续被弹幕命中时，中屏飘字会堆叠（「-1.8 秒」「看准反拍！」重复多层）；
2. 桌面端两侧留白较大，属于移动优先的预期行为，但可考虑加背景装饰或键位提示；
3. 结算页统计信息偏少，可加「整蛊次数 / 最短用时 / 最佳连击」；
4. 章节之间缺少过场，纯选关页跳转，叙事连贯性可加强；
5. 音频是程序化循环，长时间游玩可能疲劳，需要更多曲目变奏或环境音。

### Q45：下一版本优先级建议？

| 优先级 | 事项 | 理由 |
| --- | --- | --- |
| P0 | 清理死代码、补 README/设计文档 | 降低维护与交接成本 |
| P1 | 修复飘字堆叠、完善结算统计 | 直接影响手感与复玩动力 |
| P1 | 接入 SDK 存档/排行榜 | 让进度跟随玩家，形成长期目标 |
| P2 | 增加 2–3 个新关卡或模式变奏 | 延长内容寿命 |
| P2 | 章节过场与 Boss 演出升级 | 提升叙事与情绪峰值 |
| P3 | 用生成/手绘资源替换角色与背景 | 提升美术上限，但成本最高 |
