# Flutter 3D 技术验证闭环

## 背景与问题

当前项目是基于 Vue 3、Three.js 和 Rapier 的浏览器 3D 游戏，目标是重构为可同时上架 iOS 与 Android 的真正移动端 App。现有网页实现不能直接作为最终产品形态，且 Flutter 3D 的渲染、物理、手势和真机性能是否满足产品目标尚未被项目实际验证。

如果在完整重构后才发现 Flutter 3D 无法满足主流中高端设备的流畅体验，老板拖拽、物理连锁和竖屏手势等核心能力将产生较高返工成本。因此需要先验证最关键的技术风险。

## 期望结果

形成一个可在 iOS 16+ 与 Android 11+ 真机运行的 Flutter 3D 技术验证闭环，并以可观察结果判断 Flutter 3D 是否能够承载本项目的核心游戏体验。验证结论应足以支持继续使用 Flutter 3D，或在投入完整内容开发前切换到 Godot/Unity。

## 包含

- 移动端 Flutter 3D 基础运行能力验证。
- 程序化几何体、材质、灯光、相机、粒子和基础动画验证。
- 动态物理对象、碰撞、冲量、射线命中和连锁反应验证。
- 老板身体命中、拖拽、投掷和甩动验证。
- 竖屏手势优先交互，以及点击、长按、松手、滑动和双指操作验证。
- 基础道具动作、音频、触觉和镜头反馈验证。
- App 前后台暂停与恢复验证。
- iOS/Android 代表性真机的流畅度、稳定性和资源消耗观察。
- 形成 Flutter 3D 继续推进或评估 Godot/Unity 的技术决策依据。

## 不包含

- 完整游戏内容重构，包括全部 8 种道具、完整办公室和完整视觉表现；这些属于后续阶段。
- 广告、数据统计、分享和去广告内购；这些属于 CR-002 方向的独立商业化范围，尚未创建。
- 账号、云端存档和跨设备同步；它们不在已确认的产品范围内。
- 正式商店发布材料、运营配置和商业化合规；这些属于后续发布阶段。
- 将纯 WebView 或网页壳作为最终方案；该方向不符合已确认的产品目标。

## 影响范围

- **业务**：决定移动端 3D 游戏是否继续采用 Flutter 作为首选技术。
- **系统能力**：涉及应用壳与生命周期、游戏运行时、3D 场景与物理、多感官反馈和本地状态边界的技术可行性验证。
- **平台**：涉及 iOS 16+、Android 11+、竖屏、前后台生命周期、触觉和音频能力。
- **数据**：只需要验证会话状态和本地数据边界，不改变已确认的本地保存范围。
- **接口与契约**：需要确认渲染/物理事件、手势事件、暂停恢复事件和反馈事件能够保持模块解耦；不在本 Proposal 中定义具体签名。
- **测试**：需要真机验证渲染、物理、交互、生命周期、稳定性和性能。
- **文档**：验证结论需要反馈到 Blueprint、Roadmap 和后续技术决策中。

## 决定

### 已确认选择

- 首版必须是真正的 iOS/Android 移动端 App，不接受纯 WebView/网页壳。
- Flutter 3D 是首选方案，但不是不可替换的强制方案。
- 先验证最大技术风险，再进入完整游戏内容开发。
- 目标平台为 iOS 16+ 和 Android 11+，重点保障近几年中高端设备。
- 首版以竖屏和手势优先为主要交互方向。
- 游戏核心必须离线可玩。
- 如果 Flutter 3D 的关键能力或真机性能不达标，则评估 Godot 或 Unity，而不是降低已确认的核心游戏能力。

### 未采用方向与原因

- **纯 WebView/网页壳**：无法满足真正移动端 App 的产品目标，并存在应用商店审核风险。
- **一开始直接完整重构全部游戏内容**：在 Flutter 3D 可行性未经验证前会放大返工成本。
- **立即锁定 Godot 或 Unity**：当前 Flutter 3D 仍应先作为首选进行验证，只有验证失败才切换。
