# Project Roadmap

## 排序原则

1. **先验证最大风险**：Flutter 3D、物理、手势和移动端性能是当前最重要的未知因素，必须在完整重构前用真机闭环验证。
2. **优先形成可验收的纵向切片**：每个阶段都应产出可以运行、演示或验收的系统状态，而不是只完成某个技术层。
3. **先游戏核心，后商业化**：核心游戏必须离线可玩，商业化能力依赖结算快照和事件边界，因此排在核心玩法之后。
4. **先基础可行性，后体验扩展**：先证明渲染、物理、输入和生命周期可行，再扩展完整道具、视觉、音频和平台能力。
5. **降低返工成本**：如果 Flutter 3D 技术验证失败，应在投入完整内容制作前切换到 Godot 或 Unity。
6. **兼顾产品化发布**：核心体验稳定后，再补齐最小商业化、平台合规和发布硬化。

## 阶段一：Flutter 3D 技术验证闭环

目标：在 iOS 16+ 和 Android 11+ 真机上，验证 Flutter 3D 是否能够支撑本项目的核心交互、物理和性能目标；若不满足，则保留产品能力边界并评估 Godot/Unity。

## 依赖与风险

- 阶段一是阶段二及后续阶段的技术入口；如果 Flutter 3D 未达到真机性能或稳定性目标，后续阶段需要切换 Godot 或 Unity。
- 阶段二必须先形成结算快照和事件边界，阶段五才能在不侵入游戏规则的情况下接入商业化。
- 完整程序化几何体、材质、灯光、粒子和物理对象数量可能超过移动端预算，需要在阶段一持续测量。
- 单指手势同时承担攻击、蓄力、拖拽和瞄准，必须在阶段一验证交互冲突，否则会影响整个竖屏体验。
- iOS 与 Android 的 GPU、触觉、音频、生命周期和内购行为存在平台差异，不能只依赖模拟器验收。
- 核心游戏需要离线可玩，商业化和统计不可成为启动、游玩或结算的硬依赖。
- Roadmap 中后续阶段保持粗粒度，进入对应阶段后再通过 change 细化具体契约和任务。
